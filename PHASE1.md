# Phase 1: manual payment to Telegram

Both repositories must use the same Neon database. The website and Telegram
admin buttons now call `review_payment`; no Telegram call grants membership.

## Behavior

1. A subscriber submits a hash or screenshot and opens the private Start link.
   The 48-character random bearer token binds the submission to their numeric
   Telegram ID exactly once. Username changes cannot redirect access. Never
   publish or forward this link. Guessable `CE-123` links are no longer accepted.
2. An admin verifies the real transaction manually: chain, recipient, amount and
   confirmations. Website review asks for the verified hash, including for
   screenshot-only submissions. Telegram's two-step approval uses the submitted
   hash; use website review to supply/correct it. Hash syntax is not verification.
3. The database locks the submission, claims the normalized hash on its network,
   extends membership by 30 days from `max(current expiry, now)`, and queues a
   delivery in one transaction. Same-decision retries do not extend access again;
   opposite decisions conflict. Rejected payments grant nothing.
4. The Auto worker polls durable deliveries, unbans renewed subscribers, creates
   a join-request invitation and sends it. The worker approves a join only for the
   bound Telegram ID with an active membership and the matching unexpired link.
   Forwarded invitations cannot grant access to a different account.
5. Failure leaves delivery pending with an attempt count, error code, and retry
   time. Backoff starts at 30 seconds and caps at one hour, honoring Telegram's
   longer `retry_after`. Blocking the bot remains retryable; unblock and reuse the
   original Start link. Reopening it also requests a fresh invitation if the last
   delivered invitation expired. Invitations last up to 24 hours, bounded by the
   membership expiry. Admin status shows delivery state and attempts.
6. Expiry runs every minute. It rechecks expiry while holding the same per-user
   lock as renewals, bans expired subscribers, and records removal only after a
   successful Telegram response. Failed bans retry. Renewal delivery unbans.

Membership grants are exactly once per payment. Telegram delivery is at least
once: a lost API response or crash around commit can duplicate a message or
create an unused invitation. Repeated delivery never grants another 30 days.
The database decides membership; a Telegram outage does not restart the term.
A persistent inability to contact Telegram can delay removal after expiry.

## Controlled rollout (not executed)

- Back up the database and stop the old premium worker before migration. Old
  approval code must never run alongside the new implementation.
- Test in a separate database/channel/bot first. Apply `sql/schema.sql`, then
  `sql/phase1.sql` explicitly. The worker checks schema but never migrates it.
- Migration is transactional and rerunnable. It deliberately aborts on existing
  duplicate normalized transaction hashes. Investigate and reconcile duplicates
  before retrying; do not delete payment history casually.
- Historical approvals are not automatically regranted or requeued: older bot
  approvals may already have extended membership, while website approvals may
  have granted nothing. Reconcile each against the actual membership and payment
  history before adding any missing grant/delivery. Repeating a historical
  approval without a delivery raises a reconciliation error.
- Old pending submissions lack private tokens. After confirming the requester,
  an operator can assign a freshly generated 24-byte random hex `link_token` and
  privately give that subscriber their new bot Start URL. Never bind by username
  or by a public reference. Lost new tokens also require operator assistance.
- Website configuration stays `DATABASE_URL`, `ADMIN_TOKEN`, existing wallet
  addresses. Auto uses `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_PRIVATE_ID`,
  `TELEGRAM_PREMIUM_CHANNEL_ID`. No secret values are included in these changes.
- Use a direct/session database connection for Auto: the poller holds a session
  advisory lock to select one worker across application processes. Transaction
  pooling is unsuitable for this lock. All processes must share the same DB;
  no other application may poll this bot token or install a competing webhook.
- Bot requires invite/join-request and restrict-members permissions in the private
  premium channel. Old non-join-request invitations must be revoked by an operator
  during rollout; this change cannot control links generated by older systems.
- Deploy both compatible branches only after explicit approval. No changes to
  production secrets or database have been performed by this implementation.

## Validation

Website: `npm ci` then `npm test` (Node 20+). Database tests use isolated PGlite
PostgreSQL and execute the real schema/function, including rollback, duplicate
hash normalization, repeat decisions, rejection, and renewals. API tests mock the
Neon client. PGlite uses one connection; multi-session lock contention still
needs staging validation on PostgreSQL.

Auto: `python -m unittest discover -s tests -v`. Telegram and database clients are
mocked; tests require no credentials or external requests. Compile with
`python -m py_compile premium_bot.py`.

Before production, exercise website and Telegram approval against one staging
PostgreSQL database, simultaneous approvals/renewals and expiry from independent
connections, real Telegram permissions/join requests, blocked/unblocked messages,
expired invitation reissue, and a worker restart. Automated tests do not certify
live Telegram delivery or deployment configuration.

## Staging-specific configuration

Set `TELEGRAM_BOT_USERNAME` in the Vercel staging/branch preview environment
(without @) to the dedicated test bot. The default stays `thetce_bot`. Use the
schema-only Neon staging branch and separate admin/test bot credentials.

For a Railway test service, set the start command to
`python run_premium_worker.py`. This runs membership handling only and does not
import `main.py` or start the trading application. Configure only the four
premium worker variables listed above, using test destinations exclusively.
